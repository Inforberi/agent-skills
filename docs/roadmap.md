# План развития Agent Skills

Один раз подключите набор в чате проекта. Дальше описывайте задачи обычным текстом. Агент подбирает скиллы по задаче, а способ выполнения зависит от риска, возможностей клиента и практики проекта.

Набор описывает подключение профилей из закреплённой ревизии, пробное делегирование с разрешения пользователя и добровольный учёт результатов. Включение делегирования для конкретных типов задач зависит от данных реальной работы. [Быстрый старт](../README.md)

## 1. Сделать установку предсказуемой

- `setup-agent-skills` и `deliver-feature` используют общий порядок. Агент берёт доступный профиль или подключает его по правилу проекта и продолжает задачу в том же чате.
- При настройке агент записывает ревизию для новых установок. Доустановка и восстановление используют ту же ревизию. При повторной настройке агент сохраняет существующие инструкции и добавляет недостающие скиллы.
- Проверки ссылок и имён профилей включены в конфигурацию CI. Перед выпуском отдельно проверить в каждом заявленном клиенте первичную и повторную настройку, восстановление после прерывания и продолжение работы в новом чате.

## 2. Выбирать объём работы по задаче

| Задача | Действие |
| --- | --- |
| Локальная правка с понятным результатом | Текущий агент сразу правит и делает целевую проверку. |
| Самостоятельный блок с ясным контрактом и проверяемым результатом | При разрешении и поддержке клиента основная модель может передать блок одному исполнителю на младшей модели. Она передаёт цель, границы и команду проверки, затем принимает результат по diff и проверке. |
| Неясная причина, общий контракт, платежи, права или миграции | Основная модель разбирает задачу и отвечает за проверки затронутого риска. |

В общих инструкциях используем термины «младшая модель» и «основная модель». Конкретную модель и глубину рассуждения задаёт клиент. Если клиент не поддерживает выбор модели или делегирование, текущий агент продолжает сам. При ошибке исполнителя основная модель подхватывает его правки и результаты проверок. На старте достаточно одной попытки делегирования. Дополнительный уровень рассуждения имеет смысл рассматривать по накопленным результатам.

## 3. Уточнять правила по результатам реальной работы

Основной источник данных — обычные задачи, которые и так нужно выполнить. После проверяемой задачи фиксируем краткую запись.

| Что записываем | Как используем |
| --- | --- |
| Тип задачи, клиент, роль исполнителя, фактическая модель и глубина, если видны | Сравниваем похожие задачи при сопоставимых настройках. |
| Приёмка с первой попытки, причина сбоя и переделка | Отличаем ошибки исполнителя от проблем окружения или требований. |
| Время до приёмки, токены и стоимость при наличии данных | Учитываем постановку, выполнение, приёмку и переделки всех участников. |

Начать можно с одной локальной таблицы. Устойчивые результаты становятся основанием обновить явное правило проекта. Если полных данных о расходе нет, оцениваем качество и время, а стоимость оставляем неизвестной. Парное сравнение оставляем для случаев, когда данных реальной работы недостаточно для решения. ## Порядок внедрения

1. Проверить установку и совместимость с клиентами перед выпуском.
2. Применить быстрый путь и пробный маршрут делегирования на выбранных реальных задачах с разрешения пользователя.
3. Сделать делегирование обычным для конкретных типов задач, если реальные результаты подтверждают сопоставимое качество, меньшую общую стоимость и приемлемое время. Для остальных задач сохранять прямое выполнение.
