# Парные оценки инструкций

Для выбора исполнителя сначала используйте результаты обычных задач. После приёмки фиксируйте маршрут, качество, время и суммарный расход при наличии данных. Парные запуски нужны, когда сопоставимых записей недостаточно для решения. [Шаблон журнала реальных задач](../skills/deliver-feature/references/task-results.md)

Сравнивайте базовую и новую версии на одинаковых задачах. Таблица содержит заготовки. Перед замером привяжите каждую к обезличенному снимку реального проекта и закрепите точный запрос, исходную ревизию, материалы, тестовые данные и проверку приёмки. Используйте только изолированные копии и тестовые сервисы.

### Пилот без внешнего проекта

Возьмите исходники `agent-skills` из ревизии `e40876f` и используйте их в двух чистых копиях. В B замените инструкции и папку `skills/` проверяемой версией. Запрос для обеих копий:

> Используй локальный скилл skills/deliver-feature/SKILL.md. В examples/acceptance.md переименуй заголовок «CRM без макета» в «Очередь заявок CRM».

Приёмка сравнивает каждую копию с её снимком до запуска. В `examples/acceptance.md` меняется только строка заголовка, остальные файлы копии сохраняются. Пилот проверяет сбор метрик на небольшой правке.

## Порядок запуска

1. Зафиксируйте две версии инструкций с точной ревизией или сохранённым снимком. Для каждой задачи восстановите по две чистые копии одного снимка приложения. Подключите в A старый набор, в B новый, включая `AGENTS.md`. Остальные проектные инструкции, модель, уровень рассуждения, клиент, инструменты, бюджеты, доступы и окружение должны совпадать. Фиксируйте исходные значения один раз для серии.
2. Начинайте каждый запуск в новой сессии без предыдущей истории. В обеих ветках используйте один и тот же запрос без подсказок о стратегии. Чередуйте, какая версия запускается первой. Подготовку окружения проводите до запуска. По возможности повторите пары, чтобы видеть разброс.
3. Проверьте оба результата одной процедурой приёмки, по возможности без сведений о версии инструкций. Зафиксируйте, прошёл ли первый ответ без правок, сколько потребовалось вмешательств и сколько времени ушло до первой принятой версии. Для незавершённых запусков укажите лимит и причину.
4. Снимайте токены и количество вызовов из отчёта или журнала клиента. Считайте вызовы по одной единице в обеих версиях, включая вложенные, если клиент их показывает. Для оценки лишних вызовов отмечайте повтор без изменения входных данных, нерелевантный поиск и проверки без связи с критериями или риском. Учитывайте стоимость только при доступной разбивке токенов и одинаковом тарифе или тарифе каждого зафиксированного запуска. Недоступные метрики помечайте как «нет данных».

Сохраняйте по одной строке на запуск.

| Сценарий / повтор | Версия инструкций | Приёмка с первой попытки | Время до приёмки | Вмешательства | Токены / стоимость | Вызовы всего / лишних | Причина пропуска или ссылка на журнал |
| --- | --- | --- | --- | --- | --- | --- | --- |

Сначала сравните долю успешных первых попыток и причины регрессий. Затем сравните медианы времени, токенов и вызовов на парах, прошедших приёмку в обеих версиях. Укажите размер выборки и число пропусков. Экономия на отдельных задачах требует подтверждения на серии.
