# Deliver Feature

## Выбери глубину работы

Следуй запросу и общей политике проекта. Если запрос ограничен планом, передай план.

До реализации или делегирования проверь, однозначны ли ожидаемое поведение, границы задачи и критерии приёмки. Сначала ищи ответ в запросе, соглашениях проекта и существующем поведении. Если остаются разные трактовки, которые дадут разные результаты, спроси пользователя. Собери связанные вопросы в одно сообщение. Когда есть понятные варианты, объясни, что получит пользователь при каждом выборе, и назови рекомендуемый с причиной. Если вариантов пока не видно, задай открытый вопрос. Пока ждёшь ответа, выполняй только независимую работу.

Если пользователь просит только собрать данные, используй правила выбора исполнителя и проверки результата для этого сбора. Например, собери замеры выделенных блоков Figma и сохрани их в указанном каталоге. Реализацию начинай по запросу на реализацию.

| Режим | Как выбрать и что сделать |
| --- | --- |
| Небольшая правка | Локальный эффект, понятный результат и низкий риск. Найди причину, внеси правку, выполни целевую проверку и закончи. |
| Обычная фича | Один пользовательский сценарий с известными контрактами, даже если он затрагивает несколько файлов. Кратко зафиксируй результат и проверку, выбери нужные профили и реализуй сценарий через обычную точку входа. |
| Сложная задача | Несколько связанных сценариев, новый общий контракт, миграция с риском для данных или изменение границ доступа. До кода определи границы, зависимости и наблюдаемую приёмку. Собери и проверь первый сквозной путь до расширения реализации. |

Для небольшой правки сразу переходи к ближайшему месту изменения и целевой проверке. Подключай профиль, только если он нужен для затронутого поведения. При обнаружении нового контракта или риска пересмотри режим. После двух одинаковых сбоев пересмотри причину и следующий шаг.

Для поиска связей между модулями большого проекта используй узкий запрос к Graphify, если он уже подключён и граф актуален. Подтверждай найденные связи по исходникам. При отсутствии актуального графа продолжай поиск по коду.

## Подбери профиль

Выбирай профили сам по запросу, README и инструкциям целевого проекта. Если дизайн-задача относится к OpenPencil по запросу, документации или выбранному для неё кадру, используй профиль OpenPencil. При переносе кадра в приложение применяй также правила реализации по макету.

| Признак задачи | Что подключить, если доступно |
| --- | --- |
| Реализация по макету, изображению или визуальной спецификации | `build-from-design` и `product-ui`. |
| Работа с кадром через OpenPencil MCP | `openpencil-workflow` для замеров или правок на холсте. |
| Новый экран или поток без макета | `design-from-brief` и `product-ui`. |
| Новая тема, общие компоненты или новая UI-система | `design-system` для подготовки основы до сборки экранов. |
| Только бизнес-логика или реализация уже определённого решения | `ponytail` и инструкции проекта. |
| Решение зависит от Next.js или SvelteKit | `nextjs` или `sveltekit` для установленной версии и затронутого поведения. |
| Go API или жизненный цикл горутин | `go-backend`. |
| SQL, транзакции, блокировки или миграции PostgreSQL | `postgresql`. При изменении Go-кода на границе с БД используй оба профиля, если нужны оба контракта. |
| Жесты, анимация или особенности мобильного браузера | `apple-design` или `mobile-native` по задаче. |

Используй подходящие доступные скиллы. Если нужного профиля из набора нет и проект разрешает доустановку, вызови `setup-agent-skills` для этого профиля и прочитай его в текущем чате. При недоступной установке продолжи по проектным соглашениям в пределах применимых требований. Сторонние профили используй, когда они доступны или отдельно запрошены.

## Выбери исполнителя

На большой задаче основная модель координирует работу и несёт ответственность за конечный результат. Определи подход, порядок работ и критерии приёмки. Разбей объёмный сбор информации и реализацию на поручения с проверяемыми результатами и по умолчанию делегируй подходящие части по условиям ниже.

Перед изменением кода найди команду целевой проверки для нужного модуля. Начни с инструкций проекта, затем посмотри скрипты модуля или задачи проекта. Если готовой команды там нет, опирайся на конфигурацию тестов и CI. Сверь рабочий каталог, область проверки и доступность команды. При отсутствии подходящей команды выбери наблюдаемую проверку сценария и сообщи о границах проверки.

Локальную правку выполняй напрямую. По умолчанию передай самостоятельный блок самой младшей из доступных моделей, подходящих для этого типа задач, если одновременно выполнены условия.

- Контракт и границы правок известны, есть целевая проверка результата.
- Размер блока оправдывает время на постановку и приёмку. Например, ограниченное изменение импорта с готовым тестом подходит, а замена подписи кнопки выполняется сразу.
- В клиенте доступны субагенты и можно явно выбрать младшую модель или настроенный профиль с такой моделью. Правила среды, проекта и запрос пользователя допускают такой запуск.

Для объёмного сбора, поиска по заданному списку или сведения данных выбери исполнителя до чтения всего материала. При выполнении условий выше поручай младшей модели сбор, сверку и подготовку результата. Передай источник, объём, формат, правила для пропусков и место сохранения. Для замеров Figma укажи выделенные узлы, нужные ширины и поля таблицы. Если источник доступен только основной модели, она извлекает нужные данные и передаёт младшей доступный снимок для разбора, когда это разрешено и оправдано объёмом.

Если хотя бы одного условия нет, продолжай напрямую. Основная модель разрешает неясности в контрактах и ведёт изменения, от которых зависят права доступа, платежи, миграции или целостность данных. До запуска распредели области чтения и правок, подготовь поручения и учти предыдущие результаты по [порядку делегирования и приёмки](references/handoff.md).

## Зафиксируй приёмку сложной задачи

Сверь запрос, макет и фактическое поведение. Разреши существенные вопросы сценария, контракта или прав. Зафиксируй применимые источники данных, компоненты и состояния, а для каждого критерия — наблюдаемый результат и способ проверки.

Веди один план. Основная модель принимает спорные решения и проверяет итоговые изменения, затрагивающие права, платежи, миграции или целостность данных.

## Проверь результат

Выбери общий набор проверок по критериям и риску. Начни с кода и существующих проверок проекта. Если нужное поведение, например рендер, адаптивность или ввод, можно подтвердить только интерактивной проверкой, объясни, что проверишь, и дождись разрешения на Computer Use. Если пользователь уже разрешил эту проверку, действуй в указанных границах. Пока разрешения нет, продолжай доступные проверки и укажи, что осталось подтвердить. Для изменённого сохранения проверь запись и повторное чтение, если это часть контракта. Сверь общий diff или собранные материалы с запросом. Если результат зависит от нескольких частей, проверь их стыки и сквозной сценарий. Засчитывай проверки исполнителей и профилей, если они подтверждают критерии приёмки для итогового состояния.

Если задача подпадает под действующее правило учёта, зафиксируй [результат реальной задачи](references/task-results.md) после приёмки, включая прямое выполнение.
